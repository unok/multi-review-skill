# 実行詳細

読者: multi-review の呼び出し元。目的: 同梱 CLI の契約と、呼び出し元に残る照合・判断を参照する。
制御フロー・順序・上限は SKILL.md を正とする。Python 3.9 以上と git・diff、選択したレビュアー CLI を使う。Python の追加パッケージは不要。実行環境は POSIX（プロセス群の停止・ファイルロックを使用）。

## CLI の呼び出し（Step 1・2・4・5・6・7）

以下の `mr` は `python3 <スキルのベースディレクトリ>/scripts/mr.py`、`R` はリポジトリ外の `multi-review-<タイムスタンプ>`、`I` はその `iter-N` の絶対パスを表す。コマンドは対象プロジェクトを書き換える判断をせず、結果を stdout の JSON と成果物に残す。同一 R への同時更新は拒否する。

| コマンド・引数 | 入出力・契約 |
| --- | --- |
| `mr init R --cwd PATH [--path PATH]... [--profile default\|codex] [--roles SLUG,...] [--exclude CLI]... [--only CLI]... [--ja-review] [--ja-skill PATH] [--base-summary TEXT] [--no-standing-decisions]` | `run.json`、空の `findings.json`・`ledger.md`、`iter-1/`。常設の決定事項を取り込む（停止は `--no-standing-decisions`、「決定事項」を参照）。対象省略なら未コミット変更→デフォルトブランチとの差分。デフォルトブランチは origin/HEAD→main→master。空範囲・未検出・非 git の対象省略・複数リポジトリは中断。`--cwd` は必須、パスはそこから解釈する。対象の1行要約は `--base-summary` で保存し、省略時はブランチ名・比較元または指定パス・ファイル数を使う |
| `mr prompts I [--roles SLUG,...] [--reconsider F1,F2,...] [--ja-review\|--no-ja-review]` | 正本から `*.prompt.md`、`target.json`、`prompts.json` を生成。巨大差分は `target.diff`。次のイテレーションの準備と台帳の iteration 更新も担当。役割変更・再評価・ja-review 実行の判断を引数で渡す |
| `mr review I` | 呼び出し元がバックグラウンドで起動する。mr は全レビュアーの完了まで待つ。同時実行は最大8ジョブ。生成済みプロンプトで並列実行し、既存名の出力・試行別 stdout/stderr・`review.json` を保存。全レビュアー失敗なら終了1。一部欠席は結果に残して続行 |
| `mr collect I` | 完了した成功出力だけを解析し、位置順の `collected.json`・`collected.md` を生成。意味による重複統合・選別・台帳登録はしない |
| `mr snapshot I` | `snapshot.mode` と `snapshot.tree` または `snapshot.files`・`snapshot/`。保存済み基準の取り直しは拒否 |
| `mr inventory I [--max-bytes BYTES]` | 未解決指摘の代表位置・「他:」の対応ファイルを AST 解析し、`inventory.md` と `inventory.json` を生成。stdout と保存する JSON は `targetFiles`（対応拡張子のユニークファイル数）、`parsedFiles`、`methods`（言語別解析方式）、`unparsed`（位置・パス不正も含むファイルと理由）、`unsupported`（対象外ファイル。reason は `unsupported language`）、`truncated`。個別の解析不能は終了0、台帳不正・保存失敗は終了1。再実行開始時に旧 `inventory.md`・`inventory.json` を失効させる |
| `mr task I --input FILE` | 委譲本文を `fix-task.md` に保存。通し番号を `run.json`、番号・ハッシュを `task.json` に記録。保存失敗時も古い世代を失効させる |
| `mr fixdiff I [--after-check]` | `after.tree` 等・`fix.diff`・`fixdiff.json`。品質チェック前に通常実行し、後に `--after-check` を一度だけ実行。`changed` が真なら生成済み diff を再照合する |
| `mr ledger R add --input FILE` | 呼び出し元が選別した1件または配列を登録。ID 省略時は実行内で採番。同一入力の再実行は同一イテレーション内だけ重複登録を防ぐ |
| `mr ledger R update ID... --input FILE` | 重要度・source・file・line・problem の指定フィールドを更新。位置の除外・代表位置の変更結果を渡す |
| `mr ledger R fix ID... --iteration N --summary TEXT` | 修正済み・修正概要・現在の fixedIteration を一緒に保存 |
| `mr ledger R reject\|hold ID... --reason TEXT` | 却下・保留へ更新。理由必須。状態に不要なフィールドを除去 |
| `mr ledger R render` | `jev-guard ledger render` で `ledger.md` を生成。未導入なら同じ四状態の見出しで生成。台帳更新時も毎回 render する |
| `mr decisions R add --input FILE` | 1件または配列の決定事項を登録し、`decisions.md` を生成。入力・採番・重複防止・上限は「決定事項」を参照 |
| `mr decisions R remove ID...` | 指定した決定事項を削除し、`decisions.md` を生成。未知 ID があれば全件未削除 |
| `mr decisions R render` | `decisions.json` から `decisions.md` を生成。jev-guard は使わない |
| `mr rules I` | 条件確認・実行後、`rules.json` と生出力を保存。候補の妥当性は呼び出し元が確かめる |
| `mr gate I` | `gate.json` と生出力。必要フィールドと型、覆せる形式条件 `overruleEligible`、反証対象 `grounds` までを返す。反証・ダブルチェック・record は行わない |

終了コードは 0＝処理完了（規定の未実施・一部欠席を含む）、1＝生成・保存・データ不正 / 全レビュアー失敗、2＝引数形式不正またはゲートの API キー未設定による指示待ち、10＝rules の候補あり。0 だけでゲート採用や検査済みと判断せず、JSON の `status`・`reason` を読む。
`run.json` は実行条件の保存先で、台帳スキーマには含めない。`diffBudget` の既定は200000 bytes、超過時も全文を保存する。`timeout` は600秒、`jaTimeout` は1800秒で、いずれも `init` の同名 kebab-case オプションで設定できる。差分の上限は正の整数、時間制限は正の有限数とする。`--roles` 省略時は `pattern-consistency,naming-symmetry`（既存実装との一貫性・命名の対称性）、空文字なら専門役割なし。役割・プロファイル・除外は次のイテレーションに引き継ぐ。

## 作業ディレクトリと絶対パス（Step 4）

git ではリポジトリルート、非 git では `--cwd` を共通 cwd にする。`R` はその外に置く。パス指定が複数ルートにまたがり cwd を一意に決められなければ、呼び出し元がユーザーに確認する。プロンプト・出力は I 配下の絶対パスとし、claude / codex には stdin、agy には上限内の引数で渡す。

## 対象埋め込みの生成（Step 4）

`prompts` は未コミット変更モードで HEAD との差分・untracked 本文・ファイル一覧を含め、HEAD 不在では全対象本文を使う。ベース差分モードは merge-base と作業ツリーを比較し、累積の未コミット変更・untracked 本文を含める。パス指定は対象パスを示し、HEAD がある git の再レビューでは指定パス内の累積未コミット差分と untracked 本文に、過去の修正 diff に含まれる範囲外の変更行・ファイル一覧を加える。HEAD 不在の再レビューは指定範囲と staged・unstaged・untracked の全対象本文を合わせる。リンクは参照先のパスだけを示し、本文を読まない。非 UTF-8 のパスは、git 差分では Git の引用表記、それ以外の文書では JSON 文字列のエスケープ表記を使い、ファイル操作と台帳では元の値を保つ。全レビュアーに同じ範囲を渡し、git 差分の未変更行は指摘対象に含めない。
役割本文は `references/roles.md`、共通報告形式は SKILL.md の正本を毎回読む。再レビュー時の却下・保留一覧と直前イテレーションの修正概要は台帳から生成し、前提が変わった項目は呼び出し元が `--reconsider` で除外する。

## レビュアー実行と収集（Step 4）

`mr review I` は Claude Code の Bash では `run_in_background: true` で起動し、完了通知後に終了コードを確認する。Codex では `exec_command` の短い `yield_time_ms` で起動し、返された `session_id` を `write_stdin` に渡して終了まで待つ。完了後に `mr collect I` を実行する。

モデル・effort は SKILL.md Step 3 の表どおり明示する。claude は Read/Glob/Grep、codex は read-only の exec を使い、総合は同じプロンプトにする。総合出力は `claude.md` / `role-general.md`、専門役割は `role-<slug>.md`、source は `<cli>-<slug>`。時間制限は Python が子プロセス群に適用し、外部 timeout コマンドに依存しない。
成功条件は終了0かつ指摘形式または「問題なし」。空・挨拶だけ・解析できる指摘がない形式不正・タイムアウト・非ゼロは一度だけ再実行し、再失敗は欠席とする。空の報告は共通形式では「問題なし」、ja-review では「指摘なし」だけの行（前後の空白・句点は許容）を見出しの前で受け入れる。前置きは許容するが、指摘らしい見出しとの混在は拒否する。位置の範囲表記は先頭行を使い、余分なまとめ見出しは無視する。一部の指摘だけ解析できない場合は、その生出力と解析不能の理由も収集結果に残す。全出力が確定するまで収集しない。収集時は成功ジョブの出力ハッシュを必須とし、欠落・不一致を拒否する。試行別ログを保持し、古い出力は成功として使わない。
ja-review は呼び出し元が実行を指定し、agy と設定先スキルが存在するときだけ追加する。`prompts` の実行指定はそのイテレーションだけに適用し、省略時は `init` の設定を使う。外部スキルの prompt 正本を読み、追加行に日本語があるファイルだけを校閲対象にする。untracked は全行を対象とし、削除だけの変更・純粋な改名・非 UTF-8 のファイルは除く。100000 bytes 以下の引数バッチに分割し、元行番号を保つ。対象の1行だけで上限を超える場合は切り捨てずエラーにし、対象外の超過行は読み飛ばす。`jaTimeout` の時間制限（既定値・設定方法は「CLI の呼び出し」参照）、終了0かつ `### high|medium|low` または「指摘なし」の成功条件、一度の再試行を適用し、全バッチ失敗で欠席とする。選別は SKILL.md Step 5 と ja-review Step 4 に従い、同スキルの修正・報告工程は起動しない。
`collect` は元出力への参照と全位置を保持し、直前 `fix.diff` の実変更行の変更後番号±5に印を付ける。削除だけは削除境界が基準。直前 diff の完了記録とハッシュを検証し、検証失敗・初回・行不明・バイナリは「判定不能」（JSON null）で、近傍外（false）と区別する。

## 既存の一覧（Step 6・7）

初回委譲・差し戻し・再委譲の直前に毎回 `mr inventory I` を実行し、現在の作業ツリーから一覧を作る。台帳変更や `prompts` は一覧を失効させないため、既存の一覧を使い回さない。対象は未解決指摘の位置に挙がるファイルだけで、レビュー対象範囲の外も含む。シンボリックリンクは解析しない。構文エラー・読み取り不能・必要なコマンドやパッケージの欠落は `unparsed` に残し、ほかのファイルの解析を続ける。全ファイル解析不能でも終了0なので、件数と理由を確かめる。

Python は標準 `ast`、`.ts/.tsx/.js/.jsx/.mjs/.cjs` は TypeScript コンパイラ API、Go は `go/parser`・`go/ast` で解析する。TypeScript は対象ファイルのあるディレクトリから `run.json` の `cwd` までの `node_modules/typescript` を探し、最も近いものを使う。`createSourceFile` を持つコンパイラ API 版（TypeScript 5.x・6.x）と、7.x のネイティブ API 版に対応し、必要な API がなければ理由を `unparsed` に残す。対象ソースは実行しないが、利用者が入れた typescript パッケージは信頼して実行する。範囲外・スキル側・グローバルへの代替はしない。外部解析と Go のビルドにはコマンドごとに専用の30秒の時間制限（`INVENTORY_TIMEOUT`）を使い、Go のツールチェーン自動取得・モジュール解決は停止する。追加パッケージのインストールはしない。

モジュール変数の値は初期化式を表示し、評価しない。名前を持つネスト宣言は `Class.method` のように区別する。同じ文字列は復号後の値、数値は整数・浮動小数・bigint の種別と値で集計し、出現回数が2回以上のものを載せる。同じ行の複数出現は `L12×2` と表す。数値の -1・0・1、空文字・空白だけの文字列、真偽値・null 相当、docstring、補間文字列の断片、型内だけのリテラルは除く。補間内の式・補間なし template・f-string は含む。Go の rune・虚数、Python の複素数・bytes、TypeScript の正規表現リテラルは対象外。この除外は変数一覧には適用しない。浮動小数の指数の絶対値は10000までとし、超えるファイルは計算を展開する前に解析不能とする。

各分類の項目はコードブロックに入れ、識別子・シグネチャ・値の記号や空白・改行を Markdown 用にエスケープせずに表示する。空白・制御文字を含むファイル名は JSON で引用して表示する。囲みは内容中の最長のバッククォート列より長くする。もともと項目がない分類は「なし」、上限で省いた分類は「上限によりN件省略。」と表示する。一部を表示できた分類にも、残りの省略件数を添える。

`--max-bytes` の既定は32768 bytes（UTF-8、見出し・コードブロックの囲み・注記を含む）で、正の整数だけを受け付ける。値は120文字、シグネチャ・名前は240文字、重複の出現行は24行まで表示する。切り詰め前の値で比較する。ファイル見出しの初期配分は全体の3分の2までとし、少なくとも1分類分の容量を項目に残す。3分類に表示枠を配り、余りを再配分する。重複は回数の多い順、関数・型は指摘位置と宣言範囲の距離が小さい順、変数は宣言行が近い順を優先し、同順位はパス・行・名前で固定する。解析不能・対象外のファイル名と理由は冒頭に列挙し、出力上限に含める。省略時は件数と `truncated: true` を残す。ファイル見出しも収まらなければファイル単位で省略する。極小上限では「省略」、それも入らなければ `~` だけを出す。

## スナップショットと修正 diff（Step 6・7）

`snapshot` は初回委譲の直前に一度だけ実行する。`git diff HEAD` は元の未コミット変更を混ぜ、`git stash create` は untracked を含まないため使わない。git は HEAD または空の一時インデックスから作業ツリーの木を作り、追跡済み ignore・untracked を含め、追跡外 ignore を除く。gitlink は内部の未コミット本文を木に保存できないため、検出したら木の保存を拒否し、複製モードへ切り替える。ユーザーのインデックスをコピーしないため assume-unchanged・skip-worktree を引き継がない。ユーザーのインデックス・作業ツリー・ブランチ・refs は変えないが、参照されない blob 等を `.git/objects` に書く（通常の GC 対象）。clean フィルタ後の本文を比較する。
木の保存失敗時はレビュー対象と未解決指摘の全位置に含まれるファイルのうち、存在するファイルだけを複製し、成功した方式を `snapshot.mode` に固定する。指摘由来のディレクトリは配下のファイルへ展開する。指摘由来の不正な位置は `snapshot.json` の `excluded` に理由を記録して除外する。非 git は初めから複製モードとする。リンクはリンクとして保存し、`readlink` の値を比較する。リンク先の本文は比較しない。バイナリは外部 diff の扱いに従う。複製の再試行では保存先のリンクを外してから書き、親にリンクを含む保存先を拒否する。読み取り・保存・方式記録の失敗は成功扱いしない。
`fixdiff` は同じ方式で比較し、木の方式は色・外部 diff・textconv・rename 検出を無効にする。複製モードは Git の引用表記（空白も引用）をラベルに使う外部 `diff -uN --label` で比較し、リンクと通常ファイルの種別変更・実行ビットの変更も記録する。空ファイル削除やバイナリ変更は diff だけでは区別できないため、有無・種別・実行ビット・内容ハッシュも比較する。再レビューでは保存済みの範囲外ファイルと親 Git で本文を表せない入れ子リポジトリ内の修正 diff も対象に加え、次回のスナップショットに引き継ぐ。スナップショット外の新規ファイルは照合できない。空・古い出力は照合・ゲートに使わず、生成失敗時は完了記録を失効させる。
委譲前本文は木の方式なら `git cat-file -p "<snapshot.tree の ID>:<相対パス>"`、複製モードなら `snapshot/<相対パス>` を読む。差し戻し・再委譲でも取り直さない。

## 委譲の共通指示（Step 6・7）

inventory.md を指摘一覧の後ろに添える。一覧は指摘ファイルに限るため、下記のリポジトリ全体の検索も行う。

初回委譲・差し戻し・再委譲には、指摘一覧（指摘 ID・全位置・問題・修正案・該当する指摘の【パターン】）、`inventory.md`、`decisions.md`（決定事項がある場合）、レビュー対象範囲、作業ディレクトリ（「作業ディレクトリと絶対パス」で決定）、git と HEAD の有無、保存方式（`snapshot.mode`）、品質チェック、複製モードのスナップショット対象ファイル、失敗内容（差し戻し時）、承認内容（承認済み指摘）、以下の共通指示を渡す。範囲は「対象埋め込みの生成」に従って書き込む。「パターンの指摘」の定義は SKILL.md Step 4 を正とし、「実装前の報告」の基準は Step 5 を正とし、ブロック内はその写しとする。multi-review を実行させないのは、修正サブエージェントが CLAUDE.md / AGENTS.md の規定に従って入れ子で起動するのを防ぐためである。

呼び出し元は委譲ごとに `mr task I --input <委譲本文ファイル>` で本文を保存する。失敗は記録し、古い本文や書きかけの本文を rules 検査に使わない。

```text
指摘を解消する最小の変更をする。行を足す前に、既存文の修正・削除で対応できないか検討する。
decisions.md が添付されていれば、方針（policy）に反する修正をしない。再報告しない基準（triage）はレビュアーが報告しないための基準で、修正の制約ではない。指摘が方針と食い違う場合は直さず、「指摘ごとの対応」欄に指摘 ID・決定 ID・食い違う内容を書く。
検索は git 管理下では git grep --untracked（`--no-exclude-standard` は付けず、`.gitignore` の対象は検索しない。ビルド成果物などの生成物を拾わないため）、非 git では grep を使う。検索の実行エラーを一致なしとして扱わない。
新しい定数・関数・リテラル・ヘルパー・ファイルを書く前に、下記の自己点検の名前・重複の基準で既存のものを確認し、再利用で済むなら新設しない。公開範囲は使う場所に必要な最小にする。
指摘が挙げた位置（「他:」を含む）はレビュー対象範囲の内外にかかわらず直す。指摘の位置で不備を確認できなかった場合は、指摘 ID・位置・確認結果を「不備を確認できなかった位置」欄に書く。
パターンの指摘は、複数箇所の指摘、または書き方の不揃い・命名・エラー処理の流儀など、同じ形が他の箇所にもありうる指摘をいう。指摘一覧の【パターン】が目印。修正前にリポジトリ全体（非 git なら渡された作業ディレクトリ全体）を検索し、追加の箇所をプロンプトのレビュー対象範囲の内外に分ける。範囲内は全て直し、範囲外は直さずに「範囲外の同じパターン」欄に指摘 ID・位置を書く。「指摘ごとの対応」欄には指摘 ID・直した全箇所・修正の要約を書き、直さなかった指摘は理由を書く。
実装前の報告: 複製モードでスナップショット外のファイル（新規作成を含む）の変更が必要な指摘は、実装せずに「実装前の報告」欄に指摘 ID・必要な変更・理由を書く。それ以外で、新しい設定項目の追加、新しい状態管理の導入、外部への作用（ネットワーク・ファイル・DB スキーマ）の追加、公開 API の変更が必要な指摘も、未承認なら同じ欄に書き、実装しない。
自己点検: 修正を返す前に次を確かめ、結果を「自己点検」欄に書く。直すのはレビュー対象範囲内で今回の修正に直接関係する箇所に限り、範囲外の重複・別経路の不備・文書のずれは直さず、同じ欄に位置・内容を書く。
1. 名前: 足した・変えた名前（関数・変数・定数・キー・ファイル・テスト名）を同じ階層の兄弟と見比べ、語順・修飾・単複・動詞の選び方を揃える。新設したものは置き場所・形も揃える。
2. 重複: 添付の inventory.md を先に見て、あれば再利用する。inventory.md がない場合は検索だけで確認する。足した処理・判定・定数と同じものが既存や今回の変更の別の箇所にないか検索し、あれば1箇所にまとめる。
3. 別経路: 同じ値やフラグを使う別の経路（呼び出し元・似た分岐・兄弟の関数）で不備を見つけたら、範囲内なら直し、範囲外なら報告する。
4. テスト: 足した・変えたテストについて、「振る舞いを壊したら落ちるか」と「振る舞いを変えずに内部を書き換えたら通るか」の両方を確かめる。
5. 文書・不要なもの: 変えた挙動を説明するコメント・README などの文書を直し、使われなくなった export・分岐・間接化を消す。export の削除が公開 API の変更に当たる場合は「実装前の報告」の基準に従う。
自己点検で加えた変更の後、最後に検出した品質チェック（テスト・lint 等）を通し、「品質チェック」欄に実行したコマンドと結果を書く。品質チェックの緩和・スキップ・--no-verify は禁止。
multi-review は呼び出し元が実施するので実行しない。

返す報告は次の雛形を使い、全ての欄を埋める。該当がなければ「なし」、行わなかった項目は理由を書き、欄を省略しない。

```

## ルール検査 `mr rules`（Step 7）

品質チェック後、呼び出し元が `mr rules I` を実行する。複製モード、未導入、空 diff、最新委譲番号と本文ハッシュの不一致、本文や修正 diff の保存・読み取り失敗は未実施とする。結果の理由・エラーを最終レポートに記す。0 は候補なし、10 では呼び出し元が差分とルールに照らして真の違反があれば差し戻し、誤判定ならルール ID・判定内容・根拠を記録する。jev-guard の終了1・2等は出力を記録して続行する。誤判定が続くルールはユーザーに文言の見直しを伝える。

## 台帳 `findings.json`（Step 2・5・6・7）

指摘ごとの状態・理由を `mr ledger` で保存する唯一の正本。`jev-guard ledger render` と `jev-guard rereview` が読む。

```json
{
  "reviewId": "multi-review-<タイムスタンプ>",
  "iteration": 1,
  "findings": [
    {
      "id": "F1",
      "severity": "高",
      "source": "codex-general",
      "file": "src/register.ts",
      "line": 42,
      "problem": "email が未検証のまま DB に保存される",
      "fixSummary": "zod で email 形式を検証し、不正なら 400 を返す",
      "status": "fixed",
      "fixedIteration": 1
    },
    {
      "id": "F2",
      "severity": "低",
      "source": "claude-general",
      "file": "src/register.ts",
      "line": 10,
      "problem": "命名が不統一",
      "status": "rejected",
      "reason": "既存規約に従っている"
    }
  ]
}
```

- `id` は実行内で一意（`F1`, `F2`, …。イテレーションをまたいでも振り直さない）。`severity` は `高` / `中` / `低`。`source` は出所レビュアー（共通指摘は `,` 区切りで列挙）。
- `status` は `unresolved` / `fixed` / `on_hold` / `rejected`。`reason` は `rejected` と `on_hold` で必須、それ以外は書かない（`null` も不可）。`fixSummary` は `fixed` にしたときに書く。`fixedIteration` は修正したイテレーションの正の整数を記録する。省略された修正済み指摘は rereview の対象外。
- `iteration` は現在のイテレーション番号に更新する。
- 複数箇所の指摘は `file` / `line` に代表位置を入れ、残りは `problem` の末尾に「（他: path:line, path:line）」と列挙する。Step 7 で対応を確認した追加の箇所もここに追記し、括弧付きの「他:」がなければ新設する。不備のない位置はこの列挙から削り、残りがなければ括弧ごと削除し、代表位置を外したら `file` / `line` を選び直した位置に差し替える。フィールドや `status` の値は増やさない。`jev-guard ledger render` と `jev-guard rereview` が固定のスキーマで検証し、未知のフィールドや `status` の値をエラーで拒否するため。
- 範囲外の同じパターンはレビューの対象外で、指摘として選別しないため、台帳には記録しない。

行不明の入力は `line: null` または `"-"` とし、`mr` が `line: 1` と problem 先頭の「［行なし］」へ変換する。collect では行不明を保持する。選別後の入力には上記フィールドだけを使い、collect の raw・suggestion・locations・近傍情報は台帳に転記しない。

## 決定事項 `decisions.json`（Step 2・5・6・7・8）

呼び出し元が決めた方針と再報告しない基準の正本。R 直下に保存し、台帳のフィールドは増やさない。常設入力から取り込んだものも含め、この正本は1回の実行内で使い、コミットしない。未作成なら決定事項なしとして扱い、壊れたファイルはエラーにする。

```json
{
  "reviewId": "multi-review-<タイムスタンプ>",
  "decisions": [
    {
      "id": "D1",
      "type": "policy",
      "body": "解析器の応答形式は変えず、表示文言は各解析器が出す",
      "reason": "解析器ごとの表示契約を維持するため",
      "iteration": 1,
      "findingIds": ["F1", "F3"]
    }
  ]
}
```

`mr init` は、利用者共通の `${XDG_CONFIG_HOME:-$HOME/.config}/multi-review/decisions.json` → 対象ルートの `.multi-review/decisions.json` の順に常設入力を取り込む。git はリポジトリルート、非 git は解決済みの `--cwd` を対象ルートとする。XDG_CONFIG_HOME が未設定・空文字・相対パスなら無視し、`$HOME/.config` を使う。HOME を絶対パスで決められない場合は利用者共通の常設ファイルを不存在として扱い、プロジェクトの常設ファイルは通常どおり読む。どちらのファイルも任意で、有効なリンクは読み、壊れたリンクはエラーにする。形式は add と同じ単体オブジェクトまたは配列だが、許すフィールドは `type`・`body`・`reason` だけで、`findingIds` は空配列でも受け付けない。`--no-standing-decisions` なら探索・読み取りを行わない。プロジェクトの常設ファイルは作業ツリー専用で、コミットして共有する使い方は想定しない。Step 8 で `.multi-review/` を `.git/info/exclude` に入れると、このファイルも無視対象になる。共有が必要な決定は利用者共通のファイルに置く。未追跡の常設ファイルをレビュー対象にしたくなければ `.git/info/exclude` か `.gitignore` に入れる。追跡済みなら `--path` で対象を絞る。

取り込みは add と同じ検証・採番・重複防止・上限を使い、全件を検証してから保存する。不正入力はファイルパスと要素位置（配列は0始まりの `[n]`、単体は `[0]`）を診断して終了1。JSON の解析失敗はファイルと解析エラーを示す。init の保存失敗時も生成途中の状態ファイルを巻き戻し、R とロックは残す。取り込み0件なら decisions.json と decisions.md は作らない。常設ファイルは読み取り専用で、init 後に変更しても既存 R に再取り込みしない。

常設由来は `sources: ["user"]` または `["project"]` を持ち、両方に同じ決定があれば1件にまとめて `["user", "project"]` を保持する。出所は receipt に含めず、実行中の同じ入力の add も既存 ID を返す。出所なしは実行中の決定（旧データを含む）とし、add の入力で出所を指定できない。remove は R の決定と receipt だけを削除し、常設ファイルは変えない。削除後の手動再追加は新しい ID・出所なしとなり、別の R の init では常設入力を再び取り込む。

init の stdout は run.json のキー（取り込みがあれば `decisionSequence`・`decisionImports` も含む）に `standingDecisions: {"count": 1, "sources": [{"source": "user", "path": "/absolute/path/decisions.json", "ids": ["D1"]}]}` を加える。count は重複除去後の件数、sources は読み込んだファイルを取り込み順に示し、ids は重複なしの ID 数値順。空配列のファイルも ids が空の項目として示し、不存在・取り込み停止なら項目を出さない。このサマリは run.json に保存しない。

- add の入力は `type`・`body`・`reason` と任意の `findingIds` だけ。種別は `policy`（方針）・`triage`（再報告しない基準）、本文・理由は空白だけを認めない文字列。関連指摘は同じ台帳の ID を配列で渡し、省略・空配列を許す。順序と重複を正規化する。配列の途中に不正要素があれば全件未登録とする。
- `id` は D1 から R 全体で採番し、削除後も再利用しない。`iteration` は記録時の台帳の値。`run.json` の `decisionSequence` と `decisionImports` に採番と入力の receipt を保存し、同じ入力の再実行はイテレーションをまたいでも同じ ID を返す。削除時は receipt も除き、同内容の再追加は新しい ID になる。
- stdout は台帳と同じ `{"ids":["D1"]}`。add は入力順、remove は登録順で ID を返し、render は空配列。空の入力配列は登録なし、remove の ID 省略・未知 ID はエラー。同一 R のロックと各ファイルの原子的置換を使い、run 保存時の例外では決定事項の JSON を復元する。Markdown 保存失敗は終了1とし、保存済み JSON から render で復旧する。

`decisions.md` は種別ごとに ID の数値順で本文・理由・記録イテレーション・関連指摘を表示し、常設由来には `出所: 利用者共通・プロジェクト`（該当するものだけ）を添える。空の種別見出しは出さず、全件ゼロなら「決定事項なし」。生成物であることと編集先を先頭のコメントに示し、レビュアー向けの固定指示はプロンプトに埋め込むときだけ付ける。プロンプトの節と同じ生成処理を使い、固定指示を付けた節全体の上限は8192 bytes（UTF-8、見出し・固定指示・記録情報・改行を含む）。超える add は保存前に拒否し、古い決定の統合を促す。render・prompts でも上限を検査し、切り捨てない。

通常プロンプトは役割本文・共通報告形式の後、対象本文の前に節を入れる。ja-review は外部テンプレートの後、FILE 本文の前に各バッチへ入れ、節も引数バッチの上限に数える。policy は初回から、triage は iter-2 以降だけ載せ、該当する決定がゼロなら節を出さない。decisions.md には常に両種別を載せる。`--reconsider` の対象指摘を `findingIds` に含む triage 決定は、そのプロンプトから外す。既存の却下・保留一覧は残す。決定事項に反する指摘・基準に当たる指摘は報告させず、前提が崩れている具体例を示せる場合だけ、共通報告形式の「問題:」欄、ja-review の「理由:」欄に決定 ID・入力・手順・結果を書かせる。

決定事項の変更は成果物を失効させず、記録後に `mr prompts` で作るプロンプトから効く。決定事項を変えた後に、作成済みで未実行のプロンプトがあれば `mr prompts` を実行し直す。修正担当への受け渡しは「委譲の共通指示」に従う。

## ゲート `mr gate`（Step 7）

- 実行: `mr gate I`。JSON の `status`・`verdict`・`overruleEligible`・`grounds` を読む。遷移は SKILL.md Step 7 を参照する。jev-guard の rules・rereview・ledger render は600秒で打ち切り、rules・rereview の超過は未実施とする。形式条件成立は反証完了を意味せず、終了は呼び出し元が決める。
- 結末の記録: `jev-guard record --id <verdictId> --outcome accepted`。`needed` を覆すときは `jev-guard record --id <verdictId> --outcome overruled --note '詳細は <gate-overrule.md の絶対パス>'`。`--note` には反証本文を入れず、パスはシェルの単一引用符で安全に渡す（パス内の単一引用符は `'"'"'` として渡す）。
- 判定ログは `~/.local/share/jev-guard/verdicts.jsonl`（`JEV_GUARD_LOG_DIR` で変更可）。集計は `jev-guard stats`。

### needed の根拠確認と反証

ゲートには誤判定があるため、呼び出し元が根拠を修正 diff で確かめた場合に限り覆せる。呼び出し元も早く終わらせる方向に判断しがちなため、引用と具体的な反証を必須とする。

反証の記録が残らないまま覆すのを防ぐため、次の内容を `I/gate-overrule.md` に保存する。

- 指摘: `resolved: false` の各指摘の ID と `findings[].rationale`、再判定があれば `rechecks` の該当内容を挙げ、修正 diff（`fix.diff`）の該当行・位置の引用と、それぞれの理由に答える具体的な反証を書く。
- 新リスク: `newRisk.value: true` の `newRisk.rationale` に加え、`sections[]` の `newRiskProbability >= 0.5`（jev-guard が新リスクありと判定するしきい値）の全区画の `newRiskRationale` を1つずつ挙げ、区画の `path` と各根拠への反証を書く。「差分にない」とされた修正の diff 上の位置と該当行、「テストがない」とされたテストの名前と実行結果などを示す。同一の根拠は反証を共有し、対応する全区画を明記する。
- 確認結果: 全根拠との対応と、Step 7 で行ったダブルチェックの結果を書く。根拠が欠落・不明の場合や反証できない根拠も記載する。

## 範囲外の記録 `out-of-scope.md`（Step 6・7・8）

呼び出し元は、修正済みの指摘に由来する範囲外の同じパターンだけを、レビューディレクトリ直下の `out-of-scope.md` に「- path:line（指摘 ID、iter-N）」の書式で記録する。同じ位置は行を分けず、指摘 ID とイテレーションを `（F3, F7、iter-2, iter-3）` のようにそれぞれ `,` 区切りで併記する。Step 8 は記録された行をそのまま列挙する。未作成は空として扱う。

## レポートファイル `report.md`（Step 8）

呼び出し元が台帳 `findings.json` と `out-of-scope.md` から書く。`ledger.md` は修正概要を含まないので流用しない。

```markdown
# multi-review レポート（<タイムスタンプ>）

- 対象: <Step 1 で確定した対象の1行要約>
- イテレーション: <N>（打ち切った場合はその理由）
- プロファイル: <default|codex>
- レビュアー: <起動した CLI・役割・モデル・effort> / 欠席: <なし or 一覧>
- ゲート: <イテレーションごとに「iter-1: …」と記載。ラベルと記載事項は SKILL.md Step 8 を参照>
- 品質チェック: <Step 8 のラベル>
- jev-guard rules: <検査結果・誤判定の記録、未実施の理由・エラー出力>

## 未解決（<件数>）
なし
## 修正済み（<件数>）
- F1 [中]【共通】src/register.ts:42（codex-general, claude-general）email が未検証のまま DB に保存される → 修正概要: zod で email 形式を検証し、不正なら 400 を返す（iter-1）
## 保留（<件数>）
- F3 [中] src/api.ts:10（claude-architecture）… → 保留理由: <reason>
## 却下（<件数>）
- F2 [低] src/register.ts:10（claude-general）命名が不統一 → 却下理由: 既存規約に従っている
## 範囲外の同じパターン（<件数>）
<「範囲外の記録」の書式で列挙>
```

- 台帳の指摘は1件1行。各行は指摘 ID（`F1` など）から始め、各節の中は重要度（高→中→低。同じ重要度内は指摘 ID の昇順）で並べ、複数のレビュアーからの共通指摘には【共通】を付ける。行末ラベルは節ごとに「→ 修正概要:」「→ 保留理由:」「→ 却下理由:」を使う。範囲外の同じパターンの集約は「範囲外の記録」に従う。
- 未解決は打ち切り時にだけ残り、行末は「→ 未解決理由: <差し戻しの失敗内容など>」とする。0件の節は見出しの下に「なし」と書く（上記の未解決を参照）。

### exclude への追記（Step 8）

- 判定: `git check-ignore -q .multi-review/<タイムスタンプ>/report.md` を実行する。終了コード 0（すでに無視されている）なら追記不要でそのまま書き出す。
- 追記: 終了コード 1（無視されていない）なら、`git rev-parse --git-path info/exclude` が指すパスの親ディレクトリ（`info/`）がなければ作成し、`.multi-review/` を1行追記する。作業ツリー専用の常設ファイル `.multi-review/decisions.json` も無視対象になる。追記後にもう一度 `git check-ignore -q` を実行し、無視されるようになったか確かめる。
- 追記できない（`.git` が読み取り専用など）場合、または追記しても無視されない場合（`.gitignore` の `!.multi-review/` のような否定パターンが exclude より優先される場合を含む）は、レビューディレクトリ直下に `report.md` を置き（非 git と同じ扱い）、その理由を会話の最終レポートに書く。

## 品質チェック（Step 6 の基準・Step 7 の判定）

- 実行コマンドはプロジェクトの構成ファイル（package.json / Makefile / pyproject.toml / build.gradle 等）や CLAUDE.md から検出する。検出したコマンドにはレビュアーとは分離した時間制限（1800秒目安）を前置する。品質チェックは対象プロジェクトのコードを実行するため、ユーザー自身が開発している信頼済みプロジェクトを前提とする。
- 時間制限の超過は失敗ではなく「判定不能」とする。
- 基準記録（Step 6・初回イテレーション）: 品質チェックを検出できた場合のみ委譲前に1回実行して基準結果を記録する。基準実行にも同じ時間制限（1800秒目安）を前置し、超過・実行不能なら「基準なし」とする。未検出も「基準なし」とする。
- 失敗の分類（Step 7）: 基準結果と照合して「既存の失敗」か「回帰」かを判定する。基準がない（未検出・判定不能・修正後に初めて検出）場合は回帰と断定せず「判定不能」とする。
- `.multi-review/` 配下のファイル（レポートファイル等）が原因の失敗は、基準記録・回帰判定のいずれからも除外する。
- 品質チェック前後の比較（Step 7）: 前に `mr fixdiff I`、後に `mr fixdiff I --after-check` を実行する。`changed` が真なら生成済みの修正 diff を一度だけ再照合する。同じ委譲での after-check 後の通常実行と再度の after-check は拒否する。`mr task` で新しい委譲を保存したら、完了記録を失効させて再生成を許す。委譲前スナップショットは更新しない。比較・再生成失敗は打ち切りとして扱い、古い diff を使わない。
